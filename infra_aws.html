Implementación Equivalente en Nube (AWS Free Tier)

Guía técnica para desplegar el servicio de consulta de Nodo Ruta en Amazon Web Services eliminando los puntos únicos de fallo locales y maximizando las cuotas gratuitas y créditos iniciales.

HTTPS: CloudFront (*.cloudfront.net) Balanceo: ALB Multi-AZ (/health) Cómputo: 2 × EC2 t3.micro + Docker Datos: EBS (:ro) + S3 Versionado

01 Estrategia de Costo Cero y Gobernanza Free Tier

Para cumplir la restricción de no contratar servicios pagos fuera de cuota, la arquitectura aprovecha los límites gratuitos de AWS y descarta componentes costosos innecesarios para el MVP:

  • Cuentas nuevas (Free Plan): Disponen de créditos iniciales (USD $100 ampliables hasta USD $200 completando actividades de incorporación, vigentes por 6 meses) y acceso a más de 30 servicios Always Free sin cargos inesperados mientras no se migre a plan pago.
  • Cuentas educativas / Free Tier clásico (12 meses): Incluyen hasta 750 horas/mes de EC2 (t3.micro o t2.micro), 30 GB de EBS, 750 horas/mes de Application Load Balancer, 5 GB en S3 Standard, más los niveles Always Free de CloudWatch (5 GB de logs y 10 alarmas) y CloudFront (1 TB de salida y 10M de solicitudes HTTPS/mes).
  • Servicios descartados: Se evitan EKS (Kubernetes), NAT Gateway, EFS, zonas hospedadas en Route 53 y direcciones Elastic IP sin asociar.
Rol en el reto Servicio AWS Mejora frente al entorno local Factores de consumo (sin inventar precios)
Acceso público y HTTPS Amazon CloudFront Provee HTTPS/TLS gratuito (*.cloudfront.net) sin comprar dominio ni usar Route 53. Transferencia saliente y número de solicitudes HTTPS (cubierto por Always Free).
Proxy y Salud activa Application Load Balancer (ALB) Distribuye tráfico Multi-AZ y ejecuta health checks activos sobre GET /health. Horas de funcionamiento del ALB y unidades de capacidad (LCU).
Instancias en contenedores 2 × EC2 t3.micro + Docker Separa app1 y app2 en dos Zonas de Disponibilidad distintas. Horas-instancia (2 instancias = ~2h por cada hora reloj; 375h continuas dentro de 750h/mes) + IPv4 pública.
Datos y Respaldos EBS gp3 (:ro) + S3 Versionado Desacopla los datos del cómputo y conserva versiones respaldadas con SHA-256. GB-mes en EBS (16 GB total), almacenamiento en S3 (<1 MB) y peticiones GET/PUT.
Observabilidad y Permisos CloudWatch Logs + IAM Role Centraliza logs de ambos contenedores y evita secretos estáticos en código. GB ingeridos/almacenados en CloudWatch Logs (cubierto por Always Free). IAM sin costo.

02 Arquitectura Equivalente en AWS

03 Fase 1: Almacenamiento S3, IAM y Security Groups

1.1 Crear bucket S3 con versionado y subir respaldo inicial

Sustituye <tu-equipo> por un identificador único en minúsculas:

bash
aws s3api create-bucket --bucket nodoruta-datos-<tu-equipo> --region us-east-1
aws s3api put-bucket-versioning --bucket nodoruta-datos-<tu-equipo> --versioning-configuration Status=Enabled

# Preparar datos y respaldo SHA-256 desde tu equipo local
python scripts/datos.py preparar
python scripts/datos.py respaldar

# Subir copia activa y carpeta de respaldos a S3
aws s3 cp data/pedidos.json s3://nodoruta-datos-<tu-equipo>/actual/pedidos.json
aws s3 sync respaldos/ s3://nodoruta-datos-<tu-equipo>/respaldos/

1.2 Política IAM de Mínimo Privilegio (NodoRutaEC2Role)

Crea un rol IAM para EC2 (Instance Profile) con esta política para evitar guardar credenciales en archivos .env o imágenes Docker:

json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::nodoruta-datos-<tu-equipo>",
        "arn:aws:s3:::nodoruta-datos-<tu-equipo>/*"
      ]
    },
    {
      "Effect": "Allow",
      "Action": ["logs:CreateLogGroup", "logs:CreateLogStream", "logs:PutLogEvents"],
      "Resource": "arn:aws:logs:*:*:log-group:/nodoruta/servicio:*"
    }
  ]
}

1.3 Reglas de Security Groups

  • sg-alb: Entrada TCP 80 y 443 desde 0.0.0.0/0.
  • sg-app: Entrada TCP 8080 únicamente con origen sg-alb. No abrir puerto SSH (22); administrar las instancias mediante AWS Systems Manager (Session Manager).

04 Fase 2: Despliegue de las Dos Instancias (app1 y app2)

Lanza 2 instancias EC2 t3.micro (Amazon Linux 2023, disco raíz EBS gp3 de 8 GB) ubicadas en us-east-1a y us-east-1b, con sg-app y el perfil IAM NodoRutaEC2Role.

Copia app.py y Dockerfile en /opt/nodoruta/app de cada instancia y ejecuta (cambiando app1 por app2 en la segunda EC2):

bash
# 1. Instalar e iniciar Docker
sudo dnf update -y && sudo dnf install -y docker
sudo systemctl enable --now docker

# 2. Descargar datos desde S3 hacia almacenamiento persistente externo
sudo mkdir -p /opt/nodoruta/data /opt/nodoruta/app
sudo aws s3 cp s3://nodoruta-datos-<tu-equipo>/actual/pedidos.json /opt/nodoruta/data/pedidos.json

# 3. Construir la imagen Docker
cd /opt/nodoruta/app
sudo docker build -t nodoruta-consulta:1.0 .

# 4. Ejecutar contenedor en modo solo lectura (:ro) con envío de logs a CloudWatch
# Verifica en app.py/Dockerfile la variable de entorno exacta del ID (ej. INSTANCE_ID)
sudo docker run -d \
  --name app1 \
  --restart unless-stopped \
  -p 8080:8080 \
  -e INSTANCE_ID=app1 \
  -v /opt/nodoruta/data:/app/data:ro \
  --log-driver=awslogs \
  --log-opt awslogs-region=us-east-1 \
  --log-opt awslogs-group=/nodoruta/servicio \
  --log-opt awslogs-create-group=true \
  --log-opt awslogs-stream=app1 \
  nodoruta-consulta:1.0

05 Fase 3: Balanceo Multi-AZ (ALB) y HTTPS (CloudFront)

  1. Target Group (tg-nodoruta): Tipo Instances, protocolo HTTP, puerto 8080. Configura el Health Check activo en la ruta /health, código esperado 200, intervalo 10s, umbral saludable 2 y no saludable 2. Registra ambas EC2.
  2. Application Load Balancer (alb-nodoruta): Esquema Internet-facing, subredes públicas en us-east-1a y us-east-1b, Security Group sg-alb, listener HTTP:80 hacia tg-nodoruta.
  3. Distribución CloudFront: Origen apuntando al DNS público del ALB, política de origen HTTP only, política de espectador Redirect HTTP to HTTPS y política de caché CachingDisabled para que las consultas a /pedidos y /health lleguen siempre al backend.

06 Fase 4: Pruebas (I01–I06), Plan B y Limpieza

Ejecución de pruebas contra el punto de acceso HTTPS

bash
# I01: Verificar distribución entre app1 y app2 vía CloudFront HTTPS
python scripts/verificar_servicio.py https://<id-distribucion>.cloudfront.net/pedidos --esperadas app1,app2 --salida evidencias/aws_I01.json

# I02: Detener app1 en EC2-1 (sudo docker stop app1), esperar que ALB marque Unhealthy y probar:
python scripts/verificar_servicio.py https://<id-distribucion>.cloudfront.net/pedidos --esperadas app2 --salida evidencias/aws_I02.json

# I05: Restaurar respaldo validando SHA-256 y sincronizar hacia S3 y ambas EC2
python scripts/datos.py restaurar --respaldo respaldos/ARCHIVO.json
aws s3 cp data/pedidos.json s3://nodoruta-datos-<tu-equipo>/actual/pedidos.json
Plan B (Si la cuenta educativa restringe ALB o CloudFront) Si los permisos de la cuenta educativa bloquean la creación de balanceadores o distribuciones CDN, ejecuta la demostración completa en el entorno local (infra_local.html) y presenta esta arquitectura como diseño documentado de nube, tal como autoriza la ficha del reto.
Limpieza obligatoria al finalizar las pruebas Para evitar consumir horas o créditos en reposo: deshabilita y elimina la distribución CloudFront, elimina el ALB y el Target Group, termina (Terminate) las 2 instancias EC2, vacía y elimina el bucket S3, y borra el Log Group /nodoruta/servicio en CloudWatch.
