Despliegue y Recuperación Local en Contenedores

Guía paso a paso para ejecutar el servicio de consulta de entregas de Nodo Ruta en tu computador mediante Docker Compose, proxy inverso NGINX, persistencia en modo solo lectura (:ro) y respaldo verificable con huella SHA-256.

Acceso común: http://127.0.0.1:8080 Instancias: app1 y app2 NGINX 1.28-alpine (balanceo pasivo) Presupuesto: $0

01 Alcance y Arquitectura Local

El entorno local resuelve la operación manual sobre una única instancia desplegando dos contenedores Python detrás de un punto de acceso único en NGINX, separando el archivo de datos de la capa efímera del contenedor.

Declaración obligatoria de alcance Tener dos contenedores en un mismo computador demuestra conmutación de instancias y persistencia externa, pero no proporciona alta disponibilidad real frente a la caída del computador anfitrión, del proxy único NGINX o de un fallo compartido sobre data/pedidos.json.

02 Fase 1: Preparación del Entorno y Datos

Abre una terminal en la carpeta raíz del paquete (donde se encuentra app.py) y verifica que Python 3 y el motor de contenedores estén activos.

bash
python --version
docker version
docker compose version

1.1 Preparar la copia de trabajo y el respaldo inicial

Nunca modifiques el archivo pedidos.json de la raíz. Genera la copia de trabajo en data/pedidos.json y crea inmediatamente una copia de respaldo con su firma SHA-256 en respaldos/:

bash
python scripts/datos.py preparar
python scripts/datos.py respaldar

1.2 Reconocimiento del servicio sin contenedores

Ejecuta una instancia local directa para validar las tres rutas del servicio (/, /health y /pedidos). Luego detén el proceso con Ctrl + C para dejar libre el puerto 8080.

bash
python scripts/ejecutar_local.py --puerto 8080 --id local-1
# En otra terminal o navegador:
# http://127.0.0.1:8080/
# http://127.0.0.1:8080/health
# http://127.0.0.1:8080/pedidos
# Detener con Ctrl + C antes de iniciar Docker Compose

03 Fase 2: Despliegue con Docker Compose y NGINX

El paquete incluye ayuda_opcional/compose.yaml y nginx.conf, que levantan dos réplicas (app1 y app2) detrás de NGINX 1.28-alpine.

Componente Configuración clave Justificación técnica
Dockerfile Imagen ligera Python ejecutando app.py en puerto 8080 Empaqueta el código sin incluir datos ni secretos dentro de la imagen.
app1 y app2 Volumen ../data:/app/data:ro + healthcheck en /health El montaje en solo lectura protege los datos contra escritura accidental desde la app.
NGINX Proxy Publicado únicamente en 127.0.0.1:8080:80 Limita la exposición de red al host local y usa DNS interno de Docker.
Detección pasiva proxy_next_upstream ante error/timeout NGINX conmuta a la instancia sana sin consultar /health activamente.
bash
# 1. Validar sintaxis de Compose
docker compose -f ayuda_opcional/compose.yaml config

# 2. Construir imagen e iniciar contenedores en segundo plano
docker compose -f ayuda_opcional/compose.yaml up -d --build

# 3. Verificar que app1 y app2 estén en estado (healthy)
docker compose -f ayuda_opcional/compose.yaml ps

04 Fase 3: Ejecución de Pruebas de Validación (I01 – I06)

Ejecuta las seis pruebas obligatorias en secuencia y conserva cada archivo JSON generado en evidencias/ para completar PLANTILLA_EVIDENCIAS.md.

Prueba I01 — Funcionamiento normal y distribución de solicitudes

Realiza 10 consultas secuenciales al punto de acceso común y verifica que respondan tanto app1 como app2 con código HTTP 200 y la versión esperada:

bash
python scripts/verificar_servicio.py --esperadas app1,app2 --salida evidencias/I01_inicio.json

Prueba I02 — Caída controlada de app1 y continuidad en app2

Detén únicamente app1, registra la hora de inicio/fin, comprueba que app2 atiende todas las consultas y anota si ocurre algún error transitorio en la primera petición tras la caída:

bash
docker compose -f ayuda_opcional/compose.yaml stop app1
python scripts/verificar_servicio.py --esperadas app2 --salida evidencias/I02_fallo_app1.json

Prueba I03 — Recuperación de app1

Inicia nuevamente app1, espera a que pase su healthcheck y confirma que ambas instancias vuelven a alternar respuestas:

bash
docker compose -f ayuda_opcional/compose.yaml start app1
docker compose -f ayuda_opcional/compose.yaml ps
python scripts/verificar_servicio.py --esperadas app1,app2 --salida evidencias/I03_recuperacion_app1.json

Prueba I04 — Recreación de contenedor y persistencia externa

Fuerza la recreación de app1 (destruyendo su capa efímera) y verifica que sigue leyendo los 6 pedidos y el identificador de versión desde el volumen externo del host:

bash
docker compose -f ayuda_opcional/compose.yaml up -d --force-recreate app1
python scripts/verificar_servicio.py --esperadas app1,app2 --salida evidencias/I04_recreacion_app1.json

Prueba I05 — Fallo compartido de datos (HTTP 503) y restauración SHA-256

Corrompe deliberadamente la copia de trabajo data/pedidos.json. Como ambas instancias leen ese archivo, tanto /health como /pedidos devolverán HTTP 503. Luego restaura usando el respaldo creado en la Fase 1 y mide el tiempo total de recuperación:

bash
# 1. Simular corrupción en data/pedidos.json
python scripts/datos.py simular-error

# 2. Comprobar que ambas instancias devuelven HTTP 503
python scripts/verificar_servicio.py --salida evidencias/I05_error_503.json

# 3. Restaurar verificando huella SHA-256 (reemplaza ARCHIVO.json por el nombre real en respaldos/)
python scripts/datos.py restaurar --respaldo respaldos/ARCHIVO.json

# 4. Confirmar recuperación (HTTP 200 y versión correcta)
python scripts/verificar_servicio.py --esperadas app1,app2 --salida evidencias/I05_restaurado.json

Prueba I06 — Reproducibilidad por otro integrante

Un segundo integrante del equipo repite el levantamiento o la restauración siguiendo exclusivamente estas instrucciones y documenta los tiempos y hallazgos en la bitácora.

05 Fase 4: Observabilidad, Puntos Únicos de Fallo y Limpieza

Consulta de registros y correlación

Usa los registros combinados de Compose para relacionar cada petición HTTP en NGINX con el contenedor upstream que la atendió:

bash
docker compose -f ayuda_opcional/compose.yaml logs --tail 50
docker compose -f ayuda_opcional/compose.yaml logs nginx
docker compose -f ayuda_opcional/compose.yaml logs app1 app2

Resumen de Puntos Únicos de Fallo (SPOF) y evolución a nube

SPOF en entorno local Impacto si falla Mitigación en nube (ver infra_aws.html)
Computador anfitrión Caída total de contenedores, proxy y disco local. 2 instancias EC2 t3.micro en Zonas de Disponibilidad distintas (Multi-AZ).
Proxy único NGINX Pérdida del punto de acceso común; balanceo solo pasivo. Application Load Balancer (ALB) administrado con health check activo en /health + CloudFront HTTPS.
Archivo local data/pedidos.json Error HTTP 503 simultáneo en ambas instancias si se corrompe. Almacenamiento desacoplado en Amazon S3 con versionado habilitado y validación SHA-256.

Limpieza al finalizar las pruebas

Detén y elimina los contenedores y redes creadas por Compose sin borrar tus carpetas data/, respaldos/ ni evidencias/:

bash
docker compose -f ayuda_opcional/compose.yaml down
